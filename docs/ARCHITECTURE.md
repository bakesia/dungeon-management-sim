# Dungeon Management Sim 아키텍처

## 목표

v0.1은 완성된 콘텐츠보다 데이터 기반 확장에 안전한 실행 골격을 만든다. 엔진은 시설·종족·자원의 구체적인 이름을 알지 않으며, UI는 `GameState`와 콘텐츠 정의를 읽어 표현한다.

## 책임 분리

```text
content  ── 콘텐츠 정의(자원, 시설, 종족, 직업, Tier)
types    ── 저장 상태와 콘텐츠 계약
engine   ── 순수한 상태 전이와 게임 규칙
state    ── 화면에서 사용할 파생값 selector
persistence ── 저장 인터페이스, IndexedDB, migration
ui       ── 상태 표시와 사용자 입력 전달
```

의존 방향은 `ui → state/engine → content/types`를 따른다. `engine`은 React를 import하지 않고, 콘텐츠를 추가할 때 가능한 한 엔진 파일을 수정하지 않는다.

## GameState 원칙

- 모든 저장에는 `saveVersion`이 있다.
- 시설 인스턴스는 콘텐츠 전체를 복사하지 않고 `definitionId`만 저장한다.
- 자원은 `Record<ResourceId, number>`로 저장해 새 자원을 추가할 수 있다.
- 맵은 고정 크기 2차원 배열 대신 좌표가 포함된 타일 레코드다. `floor`는 향후 다층 확장을 위한 선택 필드다.
- 인구는 종족과 직업을 분리한 집단 단위다.
- 수용량, 표시 이름 같은 파생값은 저장하지 않고 selector와 콘텐츠 정의로 계산한다.

## 상태 변경

자원·코어 HP·플래그·로그의 공통 변경은 `applyEffects`를 통한다. 이후 건설, 이벤트, 침입, 일일 정산은 `EffectDefinition[]`을 만들고 같은 처리기를 호출한다. 새로운 효과 종류는 타입과 처리기 한 곳에 추가한다.

## 하루 처리 계획

`engine/day`에는 추후 다음 단계를 각각의 함수로 구현하고 작은 오케스트레이터에서 순서대로 호출한다.

1. 생산
2. 식량 소비
3. 유지비
4. 주민 처리
5. 일반 이벤트
6. 침입
7. 결과 적용
8. Tier 판정
9. DAY 증가 및 자동 저장 요청

엔진은 브라우저 저장소를 직접 호출하지 않는다. UI/상태 계층이 턴 결과를 받은 뒤 `SaveRepository`로 저장한다.

## 저장과 마이그레이션

`SaveRepository`가 저장 매체를 추상화한다. 현재 브라우저 구현은 IndexedDB 단일 슬롯을 사용하고, 지원되지 않는 환경에서는 메모리 구현을 사용한다. 구조가 바뀌면 `saveMigrations.ts`에 이전 버전에서 다음 버전으로 올리는 순차 migration을 추가한다.
